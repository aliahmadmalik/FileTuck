# Maintainer release guide

## Decisions before first publication

Confirm the GitHub owner/repository, source license, public author identity, and
release signing key. The application ID includes `aliahmad`; this is intentionally
public metadata. Git commits also expose author name and email: choose a GitHub
no-reply email if you do not want to expose a personal email address.

Keep the release keystore and passwords outside this repository and back them up
securely. Never paste passwords or private keys into issues, chat, source files,
or shell command arguments. Future updates must use the same key. The public
certificate inside an APK is expected; its subject can expose identifying details.
Use a project identity when creating a new certificate if appropriate.

## Build and sign locally

1. Run `./gradlew clean assembleRelease lintRelease` using JDK 17.
2. In Android Studio, choose **Build > Generate Signed App Bundle or APK > APK**.
   Select the app module and an existing release keystore, or create a new keystore
   outside the project. Enter passwords in Android Studio, select the release
   variant, and note the resulting signed APK path.
3. Alternatively, align the unsigned APK and sign with SDK tools. Replace the
   example paths and alias; passwords are requested interactively:

```sh
"$ANDROID_HOME/build-tools/34.0.0/zipalign" -p -f 4 \
  app/build/outputs/apk/release/app-release-unsigned.apk /tmp/filetuck-aligned.apk
"$ANDROID_HOME/build-tools/34.0.0/apksigner" sign \
  --ks /path/outside/repository/filetuck-release.jks --ks-key-alias filetuck \
  --out /tmp/filetuck-signed.apk /tmp/filetuck-aligned.apk
./scripts/package-release.sh /tmp/filetuck-signed.apk
```

Do not use the Android debug key. The package script checks the application ID,
version, absence of requested permissions, non-debuggable flag, APK alignment,
and valid signature; it rejects the usual Android debug certificate. The script
cannot prove that an arbitrary APK matches the reviewed source: build it yourself
from the exact release commit. Review `release/SIGNING-CERTIFICATE.txt`, especially
the certificate subject, and record the signer fingerprint for future releases.

The public assets are **only**:

- `release/FileTuck-2.0.apk`
- `release/SHA256SUMS`
- `release/SIGNING-CERTIFICATE.txt`

Do not upload the whole build folder, mapping reports, machine caches, keystores,
local preferences, or debug APKs. For later releases, increase `versionCode` and
update `versionName`, release notes, documentation, and package-script expectations.

## Device verification

Use harmless sample files. Test on Android 10 and a current Android device when
available; record actual tested versions in release notes without claiming unrun tests.

- Install the signed APK and confirm the version and launcher/settings screen.
- Share one and multiple files to each destination; compare contents with sources.
- Share repeated filenames; check previous files remain intact for each provider.
- Restart FileTuck; confirm destination persistence.
- Cancel the folder picker; confirm settings are unchanged.
- Revoke folder access or delete the folder; confirm a useful error and recovery.
- Test no-file/text-only shares and inaccessible files without a crash.
- Verify a `file://` share does not copy app-private files or any other raw path.
- Exercise partial failure and a large file; check that behavior matches README limits.
- For subsequent releases, install over the previous release and verify retained settings.

## Review source before publishing

This preparation started from a directory with no Git history. Before the first
push, initialize Git and explicitly stage the source and documentation only:

```sh
git init -b main
git add .gitignore .gitattributes .github README.md docs scripts app/src app/build.gradle.kts \
  app/proguard-rules.pro build.gradle.kts settings.gradle.kts gradle.properties \
  gradlew gradlew.bat gradle/wrapper
# Add LICENSE separately after the owner chooses one.
git diff --cached --stat
git diff --cached --check
git diff --cached
```

Inspect the actual staged filenames and contents for tokens, credentials, personal
paths, keys, and unintended files. Run a dedicated secret scanner if available.
Pattern scanning cannot guarantee absence of every secret. `.gitignore` does not
remove previously tracked files or secrets in history. Review the staged binary
wrapper JAR against the wrapper generated by the trusted Gradle distribution.

## Publish on GitHub

Authenticate locally with `gh auth login --hostname github.com --web`; do not send
a token in chat. Confirm `gh auth status`, repository ownership, the source license,
and the commit author before committing and pushing. Create a public repository
under the confirmed owner, push the reviewed commit, and wait for CI to pass.

Tag that tested commit `v2.0`. Create a **draft** GitHub release for that tag with
`docs/RELEASE-NOTES-2.0.md` as its description, attach the three verified assets,
check installation and download integrity, and publish the release. GitHub’s
automatic source archives are not substitutes for the APK asset.

Once the repository URL is known, update README with a direct Releases link.
Enable/check GitHub secret scanning and push protection in repository settings.
CI here deliberately has no signing credentials and never uploads a release.

References: [Android app signing](https://developer.android.com/studio/publish/app-signing),
[apksigner](https://developer.android.com/tools/apksigner), and
[GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).
